二、七虾定义

1. 门虾 gate — 纯对话界面

S 级量化判断标准（4条件判断树）

门虾收到用户消息后，按以下判断树决定自己答还是派策虾。必须同时满足全部4个条件才是 S 级：

#条件不满足示例
1纯信息查询/问答/闲聊（不产生文件、不修改代码、不计算数据）「帮我写个BP」→ 非S
2无需读取本地文件即可回答「看看上次那个方案」→ 非S
3回复 ≤150字（约3-4句话）需要详细解释的 → 非S
4无需联网搜索或超出训练数据的外部知识「今天苹果股价」→ 非S

任一不满足 → sessions_spawn(agentId: "plan") → 「收到，策虾在处理了」

门虾同时负责识别控制指令：取消/停下/不用了→取消链路。紧急/马上/立刻→P0抢占。

五、回流与容错链路

5.1 审虾打回回流

审虾 V6-TCS < 65
  │
  ▼
策虾收到打回 + 问题清单（具体扣分项和原因）
  │
  ├─ 第1次打回：分析问题 → minor fix(同虾修改) / major fix(换虾重做) → 再审
  ├─ 第2次打回：换模型(Sonnet→Opus) 或 换策略(拆分更细) → 再审
  └─ 第3次仍<65：升级用户决策
        ├─ 用户接受 → 标记「用户豁免」交付，记虾记录
        ├─ 用户继续 → 策虾重新出方案（重置打回计数）
        └─ 用户放弃 → 任务关闭，记虾记录+标注原因

5.2 用户反馈回流

用户：「这个不对/不好/改一下XX」
  → 门虾识别为反馈（非新任务）→ sessions_send 策虾
  → 策虾判断：轻量(自改) / 重做(spawn虾) / 澄清(反问)
  → 修改 → 交付 → 用户确认

最终交付责任人：策虾。问责链：用户→门虾→策虾→执行虾。审虾是质量顾问，不对交付负责。

六、任务控制机制

6.1 错误重试

故障类型重试策略
sessions_spawn 失败自动重试1次(5s间隔)→仍失败→通知门虾告知用户「系统忙，稍后重试」
执行虾超时策虾检查部分产出→有价值汇总交付 / 无价值→换虾重试1次
执行虾异常(非0 exit)策虾读错误→可自动修复→同虾重试 / 不可修复→换虾或降级需求
模型不可用(限流/宕机)自动 fallback(Opus→Sonnet→Haiku)→降级标注→记虾记录→成本补偿
Cron 失败(记虾/审虾)下次Cron自动补跑(检查上次成功时间戳，>2倍间隔→触发补跑)

6.2 任务取消

用户：「取消/停下/不用了/stop」
  → 门虾识别 → sessions_send 策虾 {action:"cancel"}
  → 策虾 /subagents kill all (cascade)
  → 策虾→门虾：「已取消。完成:XX。未完成:YY。」
  → 门虾→用户

6.3 优先级抢占

级触发词行为
P0 紧急「紧急/马上/立刻/urgent」门虾通知策虾暂停当前→新任务优先→旧任务排队恢复
P1 普通默认FIFO排队，不打断进行中
P2 后台「有空再做/不急」入后台队列，Cron空闲时段自动执行

6.4 超时保护

级超时行为
A300s策虾检查部分产出→有价值汇总/无价值重试1次
B600s同上
C900s有价值汇总+标记不完整 / 无价值换模型重试1次
D1800s各分身已完成→先交付 / 超时分身→换策略重试1次

七、Agent间通信容错规格

通信类型超时重试降级
门虾→策虾 spawn30s重试1次(5s)→告知用户「系统忙，稍后重试」
策虾→执行虾 spawn30s重试1次→换虾降级需求范围
策虾→审虾 spawn30s重试1次→跳过审查(标记)交付标注「未经审查」
执行虾→策虾 announcerunTimeout+60s网关自动重试队列sessions_history回拉
审虾→记虾 数据抄送30s记虾下次Cron补扫(幂等)不阻塞主链路
任意→任意 sessions_send15s重试1次→死信队列记虾Cron重投

7.1 死信队列运营规则 [V6.0.2 新增]

存储位置：~/.openclaw/workspace/.dead-letter/，每条死信为独立 JSON 文件。

死信条目结构：

{
  "id": "dl-YYYYMMDD-NNN",
  "createdAt": "ISO-8601",
  "source": "senderAgentId",
  "target": "receiverAgentId",
  "type": "sessions_send|announce|data_copy",
  "payload": { ... },
  "retryCount": 0,
  "lastRetryAt": null,
  "status": "pending"
}

重试与降级策略

重试次数间隔行为
第1次创建后5分钟记虾 Cron 自动重投。成功→标记 resolved
第2次上次重试后15分钟记虾 Cron 自动重投。成功→标记 resolved
第3次上次重试后60分钟记虾 Cron 自动重投。成功→标记 resolved
3次全部失败—标记 lost。提取关键信息→写入当日 memory/YYYY-MM-DD.md 丢失记录。原始死信归档到 .dead-letter/.archive/（保留30天）

告警触发阈值

条件级别动作
死信队列 pending >5条（24h内累积）⚠ 警告记虾次日 Cron 写入 MEMORY.md 告警标记。门虾下次对话时主动提醒用户
死信队列 pending >10条（24h内累积）🔴 严重记虾立即（不等 Cron）sessions_send 门虾「系统通信异常，死信队列积压>10条」。门虾主动通知用户。记入 V6 缺陷文档（P1）
同一通信类型 lost >3条（7天内）⚠ 警告记虾标记该通信类型为「通信瓶颈」。记入 V6 缺陷文档（P2）。建议策虾调整该类型通信的降级策略
连续7天死信队列为0✅ 健康记虾在周报中标注「通信健康度：优秀」

人工介入流程

  1. 死信 pending >10条 → 记虾通知门虾 → 门虾告知用户 → 用户决定：
    • 「忽略继续」→ 记虾归档所有死信为 lost（不清除），系统继续运行。下个 Cron 重新评估
    • 「暂停排查」→ 策虾暂停接受新任务（已在执行的不中断）。记虾整理死信汇总报告（按通信类型/源agent/目标agent分类）。用户排查后发「恢复」→策虾恢复
  2. 死信单条包含关键数据（如用户明确要求的归档指令）→ 标记 lost 前由记虾提取 payload 内容→尝试手动执行归档 → 标注「手动补偿」

死信清理

  • resolved 死信：保留7天后自动删除
  • lost 死信：归档到 .archive/，保留30天后自动删除
  • 每月1日清理过期归档（记虾 Cron 09:00）

8.2 熔断规则

触发条件级别动作
门虾出现阻塞事故（沉默>10s） P0 熔断 立即回滚至上一阶段。停止策虾 spawn，门虾恢复纯对话模式。排查根因→修复→重新申请进入当前阶段
策虾 spawn 连续失败 ≥5次（1h内） P0 熔断 暂停策虾。门虾告知用户「系统维护中」。排查通信/模型问题→修复→恢复。记入 V6 缺陷（P0）
执行虾输出质量断崖下降（V6-TCS均分日环比下降>20分） P1 预警 不熔断，但暂停新任务进入该虾。审虾回溯最近10个任务→分析原因（模型升级？prompt变更？）→修复→恢复。记入 V6 缺陷
死信队列 pending >10条（24h） P1 预警 不熔断，触发人工介入。按 §七.7.1 死信告警流程处理。不影响正常任务链路
同一执行虾连续3次被打回（V6-TCS <65） P1 预警 冻结该虾。策虾停止向该虾派任务。审虾检查其最近10个任务→判断是模型问题/上下文污染/任务不匹配→修复→解冻。记入 V6 缺陷
用户满意度日环比下降>30% P1 预警 不熔断。审虾回溯当日所有交付→定位问题→提出修复建议。记虾记录趋势

8.3 回滚流程

  1. 触发熔断 → 门虾立即收到通知（sessions_send from 审虾/记虾/策虾）
  2. 门虾告知用户：「系统检测到异常，已暂停XX功能。其他功能正常。」
  3. 回滚操作：
    • G3→G2：策虾停止 spawn 算虾/工虾/审虾。A/B级笔虾任务继续。Cron 保留记虾（文件管理+追踪不中断）。
    • G2→G1：策虾停止接受新任务。已完成的任务正常交付。门虾恢复纯对话模式。
    • G1→下线：门虾停止运行。用户直接使用底层 Claude Code。
  4. 修复验证：在回滚后的稳定阶段修复根因→人工验证（至少5个测试用例）→重新申请进入下一阶段
