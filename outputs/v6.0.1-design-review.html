二、七虾定义

1. 门虾 gate — 纯对话界面

[V6.0.1 新增] S 级量化判断标准

门虾收到用户消息后，按以下判断树决定自己答还是派策虾。必须同时满足全部4个条件才是 S 级：

#条件不满足示例
1纯信息查询/问答/闲聊（不产生文件、不修改代码、不计算数据）「帮我写个BP」→ 非S
2无需读取本地文件即可回答「看看上次那个方案」→ 非S
3回复 ≤150字（约3-4句话）需要详细解释的 → 非S
4无需联网搜索或超出训练数据的外部知识「今天苹果股价」→ 非S

任一条件不满足 → sessions_spawn(agentId: "plan") → 回复「收到，策虾在处理了」

此外门虾负责识别用户控制指令：取消/停下/不用了 → 触发取消链路（§十.2）。紧急/马上/立刻 → 触发优先级抢占（§十.3）。

2. 策虾 plan — 系统大脑

[V6.0.1 新增] 策虾是最终交付责任人。无论执行虾和审虾的结果如何，策虾负责整合、判断、最终交付门虾。交付质量有问题的第一问责对象是策虾。

配置项值
模型anthropic/claude-sonnet-4-6
D级超复杂任务可切换 anthropic/claude-opus-4-7（手动/自动兜底）
maxSpawnDepth2
allowAgents["scribe", "calc", "forge", "audit"]
Sandboxoff
Workspace~/CC/

核心职责：

  1. 收任务 → S/A/B/C/D 分级（§三）
  2. 出方案 → announce 门虾（D级必等用户确认，A/B/C可并行执行+告知）
  3. 派虾 → sessions_spawn 对应执行虾
  4. sessions_yield 等待结果（不轮询）
  5. 审虾打回时 → 重新评估 → 同虾修改或换虾重做 → 再审（最多2轮）
  6. 汇总交付门虾 + 抄送记虾

三、路由派虾 S/A/B/C/D（V6.0.1 修订版）

[V6.0.1 修订] 门虾判断 S 级用四条件判断树（§二.1）。策虾收到非 S 任务后按以下规则分级：

级条件（策虾判断）策虾做法审虾超时
S 门虾已过滤。策虾收到S级说明门虾误判 → 回「这个你自己答」 立即退回门虾 否 —
A 单文件 + 单任务类型 + 无需外部数据查询 + 预估≤5分钟 spawn 1只执行虾 → 汇总交付 否 300s
B 单文件 + 单任务类型 + 可能需要查规范/数据 + 预估5-15分钟 spawn 执行虾+要求V6-TCS自评 → 汇总 否（可选） 600s
C 正式交付物（对外/竞赛/发布）+ 需要多轮验证 spawn 执行虾 → spawn 审虾审查 → 修改 → 交付 是（必调） 900s
D 多文件 或 多任务类型 或 预估>30分钟 先出方案→等用户确认→分身并行→spawn多虾→审虾终审→汇总交付 是（终审） 1800s

[V6.0.1 新增] 复合任务与模糊任务处理：

场景规则
复合任务（涉及≥2个任务类型，如论文+PPT+数据）自动升级为 D 级。策虾用分身模式并行处理。
模糊任务（策虾无法判断级别/范围/交付标准）禁止猜测。策虾必须 announce 门虾反问用户澄清（「你要的是A还是B？交付标准是？」），等用户回复后再分级。不问直接做 → 记入审虾周报违规记录。
两可任务（A/B边界或B/C边界）向上取级。A/B边界→B级，B/C边界→C级。宁可多做检查不少做。

四、V6-TCS v1.1 任务完成度评分标准

（五维度、100分制、跨任务类型通用。V6.0.1 新增复合任务加权规则。）

D1. 需求覆盖度 — 30分

分数标准
28-30完全覆盖显性+隐性需求。主动补充用户未提及但关键的边缘情况
24-27完全覆盖显性需求。大部分隐性需求触及。无遗漏
19-23覆盖所有显性需求。隐性需求未触及
14-18遗漏1项显性需求，或1项关键需求理解偏差
9-13遗漏2-3项显性需求，或核心需求理解偏差
0-3答非所问。大部分需求未满足

扣分触发：用户说了X但输出无X(-5/项)、暗示了Y但没识别(-3/项)、自作主张加用户没说的内容(-3/项)

D2. 输出正确性 — 25分

分数标准
23-25零错误。数据可溯源、逻辑完整无跳跃、代码可运行+边界测试通过、计算可复现
19-22无实质性错误。极少量不影响使用的边缘瑕疵
15-181处实质性错误
10-142-3处实质性错误
0-4核心结论错误，需完全重做

一票否决：数据造假/大段抄袭/引用不存在文献→0分，记入V6缺陷

D3. 交付质量 — 20分

分数标准
18-20超出预期。信息密度极高、零废话、结构精炼、可直接交付第三方。读起来不像AI写的
15-17达到预期。简洁清晰，少量微调(<10%改动)。无明显AI套话
11-14基本可用。有明显冗余或粗糙，需20-30%改动
7-10勉强可用。大量AI痕迹，需>50%改动
0-2完全不可用。需要重写

D4. 规范遵循度 — 15分

分数标准
13-15严格遵循所有规范。三线表/字体/字号/行距100%准确。引用一致
10-12遵循主要规范，1-2处小偏离
7-9遵循了但执行粗糙
4-6多处规范偏离
0完全不符合规范

D5. 效率与成本 — 10分

分数标准
9-10模型选择最优+路径无冗余+token效率极佳
7-8模型合理，路径基本高效，少量可优化冗余
5-6模型合理但路径有优化空间
3-4模型偏高或路径明显冗余
0严重浪费

总分等级

分数等级含义动作
95-100A+卓越直接交付。记虾记录为标杆案例
85-94A优秀微调后可用
75-84B良好局部修改
65-74C合格审虾打回1次修改
50-64D不合格打回重做。记虾记录
<50F严重失败打回重做+记入V6缺陷+策虾重评方案

[V6.0.1 新增] 用户好评加分：用户主动表示满意（「很好」「不错」「就是这样」）→ 该任务总分 +2 分（A+上限100）。用户主动表示不满意 → 总分 -5 分，强制打回策虾重新评估。

九、回流与容错链路 [V6.0.1 新增]

9.1 审虾打回回流

审虾 V6-TCS < 65
  │
  ▼
策虾收到打回 + 问题清单
  │
  ├─ 第1次打回：分析问题 → 同执行虾修改（minor fix）或换虾重做（major fix）→ 再审
  ├─ 第2次打回：换模型（如Sonnet→Opus）或换策略（拆分更细）→ 再审
  └─ 第3次仍<65：升级用户决策
        ├─ 用户接受 → 标记「用户豁免」交付
        ├─ 用户要求继续 → 策虾重新出方案（不计入打回次数）
        └─ 用户放弃 → 任务关闭，记虾记录

9.2 用户反馈回流

用户：「这个不对/不好/改一下XX」
  │
  ▼
门虾识别为反馈（非新任务）
  │
  ▼
sessions_send 策虾：「用户反馈：XX。请重新评估。」
  │
  ▼
策虾判断：轻量修改(自己来) / 需要重做(spawn执行虾) / 需要澄清(反问用户)
  │
  ▼
修改 → 交付 → 用户确认

9.3 最终交付责任人

策虾是最终交付责任人。无论执行虾和审虾的结果如何，策虾对交付给门虾（进而给用户）的内容负全责。问责链：用户→门虾→策虾→执行虾。审虾是质量顾问，不对交付负责。

十、任务控制机制 [V6.0.1 新增]

10.1 错误重试策略

故障类型重试策略
sessions_spawn 失败自动重试1次（间隔5s）→ 仍失败 → 通知门虾告知用户 + 询问是否重试
执行虾超时（runTimeoutSeconds）策虾收到 timeout announce → 检查部分产出 → 有价值→换虾继续 / 无价值→重新spawn
执行虾返回异常（非0 exit）策虾读取错误信息 → 可自动修复→同虾重试 / 不可修复→换虾或降级需求
模型不可用（provider 限流/宕机）自动切换 fallback 模型（Opus→Sonnet, Sonnet→Haiku）→ 降级标注 → 记虾记录
记虾/审虾 Cron 失败下次 Cron 周期自动补跑（检查上次成功时间戳，>2倍间隔→补跑）

10.2 任务取消链路

用户发：「取消 / 停下 / 不用了 / stop / cancel」
  │
  ▼
门虾识别取消意图（关键词匹配 + S级判断树条件1-4均不满足→非S→但仍优先处理）
  │
  ▼
门虾 → sessions_send 策虾：{ action: "cancel", taskId: "当前任务" }
  │
  ▼
策虾 → cascade kill：/subagents kill all（递归终止所有子agent）
  │
  ▼
策虾 → 门虾：「已取消。已完成部分：XX。未完成部分：YY。」
  │
  ▼
门虾 → 用户：「已取消。XX部分做完了，YY没做。」

10.3 优先级抢占

优先级触发词行为
P0 紧急「紧急/马上/立刻/urgent/asap」门虾立即 sessions_send 策虾暂停当前任务 → 新任务优先 → 旧任务恢复（或降级为后台）
P1 普通默认策虾按 FIFO 排队处理，不打断进行中任务
P2 后台「有空再做/不急/慢慢来」策虾放入后台队列，Cron 空闲时段（如凌晨）自动执行

10.4 超时保护

级别默认超时超时后行为
A 级300s (5min)策虾检查部分产出 → 有价值→汇总交付 / 无价值→重试1次
B 级600s (10min)策虾检查部分产出 → 有价值→汇总交付 / 无价值→重试1次
C 级900s (15min)策虾检查 → 有价值→汇总+标记不完整 / 无价值→换模型重试1次
D 级1800s (30min)策虾检查各分身进度 → 已完成部分先交付 / 超时部分换策略重试1次

十一、Agent间通信容错规格 [V6.0.1 新增]

通信类型超时重试降级
门虾→策虾 spawn30s重试1次(间隔5s)告知用户「系统忙，稍后重试」
策虾→执行虾 spawn30s重试1次(间隔5s)→换虾降级需求范围（如长报告拆为要点）
策虾→审虾 spawn30s重试1次→跳过审查(标记未审)交付时标注「未经审查」
执行虾→策虾 announcerunTimeout+60s自动恢复（网关重试队列）策虾 sessions_history 拉取结果
审虾→记虾 数据抄送30s记虾下次Cron补扫(幂等)不阻塞主链路
任意→任意 sessions_send15s重试1次→写死信队列记虾下次Cron检查死信

死信队列：通信失败的消息写入 ~/.openclaw/workspace/.dead-letter/，记虾每日 Cron 扫描并尝试重新投递。超过3天未投递→标记为丢失→记入V6缺陷。
