一、上下文机制 [V6.0.3 新增]

1.1 设计原则

  1. 最小注入原则：每个 agent 的 system prompt 只注入它完成任务必需的信息。绝不多注。
  2. 稳定性优先：workspace 文件越稳定 → Anthropic prompt cache 命中率越高 → 成本越低（cache read 是原价 10%）。
  3. 隔离优于共享：子 agent 默认 isolated context，只在必要时 fork（分身模式）。
  4. 短生命周期：非门虾 session 完成任务即归档，不保留长对话。

1.2 Bootstrap 文件体系

Openclaw 在每次 session 启动时从 workspace 注入以下文件到 system prompt。V6 严格控制每个文件的职责、大小、稳定性：

文件职责稳定性更新触发
SOUL.md虾格：行为铁律、沟通风格、一句话人设极高用户纠正行为偏好时 → 记虾通知策虾修改
AGENTS.md虾能：工作流规则、路由逻辑、Standing Orders高工作流优化时 → 记虾通知策虾修改
TOOLS.md虾器：工具使用技巧、通信规格、踩坑记录高新工具上线或踩坑时 → 记虾通知策虾修改
MEMORY.md虾记：持久记忆指针（非内容本身）中记虾每日归档时更新索引
USER.md用户档案：偏好、项目索引、规范路径高用户信息变化时手动更新

关键设计：MEMORY.md 只存指针，不存内容。例如 「Pegasus市场研究项目：见 memory/projects/pegasus-market.md」，而不是把整个研究内容塞进去。这保证了 system prompt 不会随记忆增长而膨胀。

1.5 子 Agent 上下文传递模式

模式Openclaw 配置Token 成本适用场景V6 默认
隔离模式 context: "isolated" 低 仅 task prompt + bootstrap 独立任务，执行虾只需知道「做什么」 ✓ 默认
分支模式 context: "fork" 高 继承父 session 全部上下文 高上下文连贯性场景（策虾分身、论文+PPT一套） 仅 D 级分身

成本影响：isolated 模式下，执行虾获取的是策虾精简后的 task prompt（通常 500-1500 chars），而不是整个策虾 session 的对话历史。一个典型的 A 级任务，isolated vs fork 的 token 差异可达 5-20 倍。

规则：fork 仅限策虾分身使用。执行虾（笔/算/工）永远用 isolated。策虾负责把上下文精炼成 task prompt 传给执行虾，而不是把整个对话 dump 过去。

1.6 Session 生命周期

Agent每日重置空闲重置完成后归档
门虾 gate04:00 新 session30min 无交互不归档（持续运行）
策虾 plan04:00 新 session15min 无交互交付后 15min 归档
笔/算/工虾每次 spawn 新 session不适用完成后 10min 归档
审虾 audit每次 spawn 新 session不适用完成后 10min 归档
记虾 memoryCron 每次新 session不适用Cron 完成后 10min 归档

为什么策虾 15min 空闲就重置？策虾是按任务生命周期运行的——一个任务结束，策虾的上下文价值归零。保留长 session 只会让 compaction 积累成本。重置 = 新 session = cache 重新命中 = 成本可控。

1.7 Compaction 策略

Agent触发阈值compaction modelmemoryFlush
门虾 gate不启用（对话简短，永不达阈值）—否
策虾 plan上下文 70% 时触发Haiku 4.5（便宜模型做摘要）是（关键决策写入 MEMORY.md 指针）
笔/算/工虾上下文 70% 时触发Haiku 4.5否

关键：compaction 用 Haiku 而非 Sonnet/Opus。摘要任务不需要强推理，Haiku 足够且便宜 10 倍以上。

二、成本优化体系 [V6.0.3 新增]

2.1 成本根因分析

Openclaw 比 Claude Code 成本高的三个根因：

#根因技术原理V6.0.3 对策
1 System prompt 过大且不稳定 Anthropic prompt cache 按前缀匹配。workspace 文件塞满→前缀太长→cache 一次写入成本极高。文件频繁修改→cache 失效→每次重写→全价 六层优化第1层：Bootstrap 预算硬限制（§一.1.3）+ 稳定性分级（§一.1.2）
2 每轮重复注入 bootstrap 默认 contextInjection: "always" 意味着每轮对话都重新注入全部 workspace 文件到 system prompt。同一个 session 的 10 轮对话→10 次 cache 写入 六层优化第3层：策虾/记虾用 continuation-skip（§一.1.4）
3 子 agent 默认继承父上下文 fork 模式把父 session 的完整对话历史 dump 给子 agent。如果父 session 有 50 轮对话，子 agent 光上下文就要付 50 轮的钱 六层优化第4层：执行虾强制 isolated，fork 仅限分身（§一.1.5）

2.2 六层成本优化体系

Layer 1: Bootstrap 预算      ← 控制 system prompt 大小
Layer 2: Cache 优化结构      ← 最大化 Anthropic prompt cache 命中率
Layer 3: 注入策略            ← continuation-skip 避免重复注入
Layer 4: 子Agent上下文        ← isolated 默认，fork 仅分身
Layer 5: Session 生命周期     ← 短命 session，及时释放上下文
Layer 6: 成本追踪与告警       ← 每日成本报告，异常波动告警

2.3 Layer 2：Cache 优化结构

Anthropic prompt cache 工作机制：

  • Cache 按 system prompt + messages 的前缀匹配
  • 前缀越稳定 → cache 命中率越高
  • Cache write：原价（一次性）
  • Cache read：原价的 10%
  • Cache 有效期：5 分钟（TTL 内复用 = 仅付 read 价）

V6 的 cache 优化策略：

  1. SOUL.md 放在 system prompt 最前面（最稳定→cache 前缀永远不变）
  2. AGENTS.md 紧随其后（高度稳定→cache 前缀偶尔更新）
  3. TOOLS.md 放在稳定块最后（中等稳定）
  4. MEMORY.md 放在可变块（每日变化→不影响前面的 cache 前缀）
  5. USER.md 放在最后（稳定但独立）

效果：SOUL.md + AGENTS.md 作为 cache 前缀，大概率跨 session 命中。即使 MEMORY.md 每日更新，前缀不变→cache 只追加写入新部分。

维度Claude Code（现状）Openclaw V6.0.3（优化后）
